## 1. What we're building

A workflow that screens hundreds of candidate books, filters them down to ones we can legally use
(public domain), scores the survivors against a researched studio adaptation mandate, and produces
a shortlist of ten. A forward-looking piece also tells us what's about to become public domain, so
we can prepare ahead of time instead of reacting after the fact.

**Order of operations matters:** we narrow to public domain first, then score. That way the scoring
step never wastes time on — or gets tempted by — a book we can't legally adapt.

| Stage | What happens |
|---|---|
| 1 | **Forward-Looking PD Calendar** — what enters public domain in each of the next 5 years, and on what date |
| 2 | **PD Verification Agent** — independently confirms each candidate book's public-domain claim |
| 3 | **Book Corpus & Data Pipeline** — the hundreds of candidate titles feeding stages 2 & 4 |
| 4 | **Studio Mandate Research & Scoring Agent** — selects a target studio, derives an evidence-based mandate, ranks PD-confirmed books |
| 5 | **Shortlist & Output** — final top-10, formatted for review |
| 6 | **Infra, QA & Docs** — repo, testing, coordination (DJ) |

### One fixed fact worth knowing up front

Under U.S. copyright law, protection for an author's work runs through December 31st of the year
their term ends — so works don't trickle into the public domain throughout the year, they all drop
on a single date: **January 1st**. The "5 years" in the Forward-Looking Calendar package means five
of these January 1st cliff-edges (this coming one, plus the following four) — not five different
dates within a year. The real work is figuring out who and what crosses each cliff, which requires
real research (author death years are often disputed and need corroboration).

## 2. Package assignments

### Package 1 — Forward-Looking PD Calendar (5-Year Horizon)
**Owner:** Teammate (phone ending 9302) · **Folder:** [`pd_calendar/`](../pd_calendar/)

Goal: for each of the next 5 January 1sts, produce a list of authors (and their works) whose U.S.
copyright protection expires, using the life-of-author + 70-years rule.

- Find a reliable source of author death years (e.g. Wikidata) and cross-check disputed ones
- Compute: an author's works enter the public domain on Jan 1 of (death year + 71)
- Cross-reference against the book corpus (Package 3) once it exists, so output is actual titles, not just names
- Output: a simple table/report — Year → Authors entering PD → Notable works

### Package 2 — PD Verification Agent
**Owner:** Teammate (phone ending 8253) · **Folder:** [`pd_verification/`](../pd_verification/)

Goal: build the independent check that confirms — or rejects — a specific book's public-domain
claim before it's allowed anywhere near the shortlist.

- Encode the U.S. public-domain rules as a deterministic rule engine (not a guess/vibe check)
- Input: one book (title, author, death year, publication year) → Output: PD confirmed / not confirmed / uncertain, with reasoning shown
- Must run independently from the scoring agent — never influenced by how "good" a book scored
- Flag anything ambiguous (disputed death year, foreign publication, renewal-era quirks 1929–1963) as "uncertain," never guess

### Package 3 — Book Corpus & Data Pipeline
**Owner:** Radoslav Raychev · **Folder:** [`book_corpus/`](../book_corpus/)

Goal: assemble the pool of hundreds of candidate books that everything else runs against.

- Source candidates (e.g. Project Gutenberg's catalog is a good starting point)
- Collect metadata the other agents need: title, author, author death year, original publication year
- Clean it up — consistent format, no duplicates, obvious errors caught
- Output: one clean file (e.g. CSV) the rest of the team can build against

### Package 4 — Studio Mandate Research & Scoring Agent
**Owner:** Chantell Ferrell · **Folder:** [`studio_scoring/`](../studio_scoring/)

Goal: select the target studio, assess what that studio is actually looking for, turn that research
into an evidence-based adaptation mandate, and build the scoring system that ranks PD-confirmed
books against it.

- Select one target studio and clearly identify it as the studio the project is optimizing for
- Assess the studio's mandate using multiple forms of evidence: purchasing/acquisition history, past adaptations and produced slate, genre/audience patterns, what it's known for
- Use online sources: trade coverage, studio/executive interviews, podcasts, panels, press releases, other credible public materials
- Separate fact from inference. Concise mandate brief with source notes, criteria we're inferring clearly labeled
- Translate the mandate into a scoring rubric and weights (genre fit, name recognition, visual/story adaptability, franchise potential, budget/scale fit, audience fit)
- Make the mandate and weights editable as a config rather than hardcoded; build the agent that takes a book + mandate criteria and produces a score with reasoning
- Output: studio mandate brief + source log + scoring config/agent

### Package 5 — Shortlist & Output Formatting
**Owner:** Luis R. · **Folder:** [`shortlist_output/`](../shortlist_output/)

Goal: take the scored, PD-confirmed books and produce the final top-10 shortlist in a clean,
shareable format.

- Combine Package 2's verification result + Package 4's score for each book
- Sort and select the top 10 (only books that passed PD verification are eligible — no exceptions)
- Output: a clean report showing rank, title, author, score reasoning, and PD verification basis for each of the 10

## 3. Getting set up (everyone, do this first)

1. Get a GitHub account if you don't have one — sign up at github.com, send DJ your username.
2. Wait for DJ's collaborator invite, accept it via email.
3. Install [GitHub Desktop](https://desktop.github.com).
4. Clone the repo: File → Clone Repository → "Domain-Hunter" → choose a folder → Clone.
5. Get access to Claude — sign in at claude.ai, ask DJ which plan/access to use.
6. Create your own branch: branch dropdown → "New Branch" → name it `yourname-packageN`

7. Open your project folder with Claude Code, or point claude.ai at your cloned files.

## 5. Ground rules

- No book goes on the final shortlist without passing Package 2's independent verification — no exceptions, even if it scores well.
- When unsure, mark it "uncertain" rather than guessing — especially for anything PD-related.
- The studio mandate must be supported by research. Package 4 should preserve source notes and distinguish observed evidence from inferred mandate criteria.
- Push back on this plan any time. It was randomly assigned by Claude to get us moving, not handed down as final.
- Questions go in the group chat — if one person is stuck, others probably will be too.

## 6. Naming — resolved

"Domain-Hunter" could read like an internet-domain search tool rather than a public-domain/free-IP
discovery engine, so the team explored a name that signals "hunt for freely adaptable IP" more
directly (one direction floated: *Farrah — The Free IP Huntress*).

**Decision:** the product is now branded **Domain Huntress**, with a new logo combining the
original book/magnifying-glass mark with an archer character — see
[`../assets/style/STYLE_GUIDE.md`](../assets/style/STYLE_GUIDE.md). The underlying GitHub repo,
folder, and branch names stay `Domain-Hunter` / `dj-development` unchanged.

## 7. How the pieces connect (data contracts)

Packages 1, 2, and 4 all depend on Package 3's corpus; Package 5 depends on Packages 2 and 4.
So the packages can be built in parallel without waiting on each other, the exact file formats
passed between them are pinned down in [`docs/data-contracts.md`](data-contracts.md) — treat that
as the interface contract. If your package needs a field that isn't in there, add it to the
contract doc and flag the change in the group chat rather than silently changing your output shape.
