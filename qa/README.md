# qa/ — pipeline contract validation

**Status:** proposed by Package 1 (Ross). This is arguably **Package 6** work — DJ's remit already
covers "spot-check each package's output before it's merged" — so it needs his sign-off on
ownership. Offered, not claimed.

Implements check 6 of [`../docs/evaluation-spec.md`](../docs/evaluation-spec.md).

## Why

Five people build five packages on five branches against one set of CSV shapes. Until now the only
thing holding those shapes together was a sentence in
[`../docs/data-contracts.md`](../docs/data-contracts.md): *"if your package needs to change one,
edit this file in your PR and call it out explicitly."* That is a social convention with no
backstop. Column names drift, `book_id` slugs come out subtly different, and nobody finds out until
Package 5 tries to join and gets zero matches.

## Run it

From the repo root, no dependencies beyond the standard library:

```bash
python3 qa/validate_contracts.py
```

Exit code is 0 on pass and 1 on failure, so it can gate a merge. `--strict` turns warnings into
failures.

Tests use `pytest`, the project-wide runner established in PR #9:

```bash
pytest qa/
```

They are `unittest.TestCase` classes, so `pytest` collects them without any adapter. Do not reach
for `python -m unittest discover` — `CLAUDE.md` rules it out project-wide, because it silently
collects zero tests from pytest-style suites and hard-crashes on directories that aren't packages.

A bare `pytest` from the repo root reaches this directory too, once PR #9 merges.

That was briefly not the case. PR #9 originally pinned
`testpaths = ["pd_verification/tests", "pd_calendar/scripts"]` — an allowlist, so `pytest` reported
`104 passed` while silently skipping all 21 tests here. Jason dropped the line in `e9be69f` once it
was raised, and a repo-root run now collects `125 passed`.

Nothing to do; recorded only because it is worth not reintroducing. An allowlist of test
directories has to be updated by hand the first time anyone adds tests anywhere new, and the
failure mode when nobody remembers is a green run that tested less than it appeared to.

## What it checks

| check | what it catches |
|---|---|
| header | a required column missing or renamed |
| enums | `pd_status`, `confidence`, bool columns holding illegal values |
| types | non-numeric years, malformed dates |
| jan-1st | a `pd_date` that isn't January 1st — terms end Dec 31, see project-plan.md §1 |
| keys | duplicate `book_id` in the corpus; a `book_id` referenced but not in `book_corpus.csv` |
| shortlist | ranks with gaps, more than 10 rows, or a row whose `pd_status` isn't `confirmed` |
| committed | a contract deliverable that is gitignored or untracked |

**Missing files are skipped, not failed.** Packages land at different times and an absent file is
not a contract violation. The report lists what was skipped, so a run that validated nothing can't
be mistaken for a clean bill of health.

## The `committed` check

This is the one worth explaining, because it's the only check that catches something a schema check
structurally cannot.

A gitignored deliverable is written perfectly on the machine that produced it and is simply absent
everywhere else. The pipeline works for its author and returns empty for everyone else — and the
package that *reads* the file looks like the broken one. There is no error message anywhere.

That exact bug reached a PR in this project (ISSUE-8: `data/studio_scores.csv` was added to the
root `.gitignore`). A schema check would never have seen it, because the file on disk was valid.

## Verified against real bugs

The suite in `test_validate_contracts.py` reproduces defects that actually reached a pull request
here and asserts the validator catches each one. A checker nobody has seen fail is
indistinguishable from one that always passes.

| test | reproduces |
|---|---|
| `test_issue_8_gitignored_deliverable` | ISSUE-8 |
| `test_issue_5_book_id_that_no_longer_resolves` | ISSUE-5 — regenerating the corpus shifted `book_id`s |
| `test_wrong_rule_gives_a_date_that_is_not_january_first` | the life+70 vs pub+95 error |
| `test_pd_gate_violation_in_the_shortlist` | the no-exceptions rule in project-plan.md §5 |

It has also been run against real pipeline output: `data/book_corpus.csv` (2,630 rows) and a
`data/pd_verification.csv` generated by Package 2 over all of them. Both passed.

## When the contract changes

Edit the `FileSpec` blocks near the top of `validate_contracts.py` — they are declarative and map
one-to-one onto the tables in `docs/data-contracts.md`. Change the contract doc and this file in
the same PR, which is the point.

Two known pending changes, both in PR #8 and not reflected here yet: the proposed `summary` /
`subjects` columns on `book_corpus.csv`, and corrected row-count figures. Neither affects
validation, since both columns would be optional.
